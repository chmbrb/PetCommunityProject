# Development

How to run PetCommunityProject locally. For why things are built this way, see the [architecture decision records](adr/README.md).

## Prerequisites

- Go 1.26+
- Node.js 26 LTS with pnpm, at the version pinned in `web/package.json` (`packageManager`). Install it with `npm install -g pnpm@<version>`.
- Docker with Compose, or Podman with a Docker-compatible socket (see [Podman](#podman))
- For the mobile apps: Android Studio (Android), or Xcode on macOS (iOS)

## Quick start

```sh
make dev-up      # Postgres + PostGIS and MinIO in containers
make migrate     # apply database migrations
make run         # API on http://localhost:8080
make web         # in another terminal: web app on http://localhost:5173
```

Open http://localhost:5173. The page should say **Connected**. The Vite dev server proxies `/api` to the Go API.

### Passkeys in development

Passkeys work on `http://localhost` because browsers treat localhost as a secure context. Use `localhost`, not `127.0.0.1`: passkeys are bound to the relying party ID, which defaults to `localhost` in development (`PC_WEBAUTHN_RP_ID`, with allowed origins in `PC_WEBAUTHN_ORIGINS`). In production both default to the instance domain.

To try sign-up without a real authenticator, use Chrome DevTools → More tools → WebAuthn, and enable a virtual authenticator with resident key and user verification support. The Go integration tests use a virtual authenticator too (`internal/server/auth_integration_test.go`).

`make help` lists every target.

## Repository layout

| Path | Contents |
|------|----------|
| `cmd/petcommunity/` | The single backend binary: `serve`, `migrate`, `healthcheck`, `version` (ADR 0003) |
| `internal/config/` | Environment-variable configuration and validation |
| `internal/database/` | Connection pool, embedded migrations (`migrations/`), SQL queries (`queries/`) |
| `internal/store/` | Go code generated by sqlc from the queries. **Don't edit by hand** |
| `internal/server/` | HTTP API (`/api/v1`), health endpoints, middleware |
| `web/` | Vue 3 + Vuetify app; `web/android` and `web/ios` are the Capacitor native projects (ADR 0018) |
| `deploy/` | Production Caddyfile; development database init scripts |
| `tools/` | Separate Go module for development tools (sqlc, govulncheck), so they don't enter the app's dependencies |
| `compose.dev.yaml` | Development services |
| `compose.yaml`, `Dockerfile` | Production deployment (preview; see below) |

## Common tasks

| Task | Command |
|------|---------|
| Unit tests (Go + web) | `make test` |
| Go tests including database integration tests | `make test-integration` (needs `make dev-up`) |
| Lint, format check, generated-code check | `make lint` |
| Go vulnerability scan | `make vuln` |
| Regenerate Go code after changing SQL | `make generate` |
| Build container images | `make images` |
| Reset the development database | `make dev-reset && make dev-up && make migrate` |

CI (`.github/workflows/ci.yml`) runs the same checks, plus golangci-lint, an Android debug build, and the container image builds.

## Upgrading runtimes

Dependabot proposes patch and minor updates. Major runtime upgrades are deliberate and skipped by Dependabot:

- **Go:** raise the `toolchain` line in both `go.mod` and `tools/go.mod` (CI installs that exact version). The vulnerability scan fails when the toolchain has known standard-library vulnerabilities, which is the usual signal to bump it.
- **Node.js:** stay on an LTS major. Change the Dockerfile base image, the CI `node-version`, `engines` in `web/package.json`, and the `@types/node` major together.
- **Postgres:** a major upgrade needs a data migration (`pg_upgrade` or dump and restore). Plan it separately.

## Conventions

- **License headers:** every source file starts with `SPDX-License-Identifier: AGPL-3.0-or-later` in its comment style (ADR 0002). Generated files and SQL query files (where sqlc would copy the comment into its output) are the exceptions.
- **Database changes:** add a new numbered file in `internal/database/migrations/` (goose format), then `make generate`. Migrations are forward-only once merged: never edit an applied migration; write a new one.
- **SQL:** queries live in `internal/database/queries/` and go through sqlc. No string-built SQL (ADR 0005).
- **API:** all endpoints sit under `/api/v1` and return JSON, with errors shaped `{"error": {"code", "message"}}`. The web app gets no private endpoints; mobile apps use the same API (ADR 0018).
- **Configuration:** `PC_*` environment variables, validated at startup (`internal/config`). Production refuses to start with missing or development values.

## Mobile apps

The native projects live in `web/android` and `web/ios` and wrap the same web build.

```sh
cd web
VITE_DEFAULT_INSTANCE_URL=https://your-instance.example pnpm cap:sync   # build + copy into native projects
pnpm exec cap open android   # or: cap open ios (macOS only)
```

Native builds must set `VITE_DEFAULT_INSTANCE_URL` until the instance picker exists. The app ID (`org.petcommunityproject.app` in `web/capacitor.config.ts`) is a **placeholder**: choose the final one before the first store upload, because it can't change afterwards.

CI builds a debug Android APK. iOS builds need a macOS runner and will be added with TestFlight in Phase 2.

## Production deployment (preview)

`compose.yaml` runs Caddy, the app, a one-shot migration, and Postgres on an internal network:

```sh
cp .env.example .env    # fill in the values
docker compose up -d --build
```

It's a **preview**: backups (ADR 0016) and media storage (ADR 0010) aren't wired in yet, so don't run a real instance on it until they are.

### Rate limits

The API limits requests per client IP address (IPv6 clients are grouped by /64 network). Defaults are in `config.DefaultRateLimits`:

| Limit | Applies to | Burst, then sustained |
|-------|------------|-----------------------|
| API | every `/api` request | 100, then 10 per second |
| Sign-in | `/api/v1/auth/login/*` | 10, then 10 per minute |
| Sign-up | `/api/v1/auth/signup/*` | 5, then 30 per hour |

Over the limit, the API answers `429 Too Many Requests` with a `Retry-After` header. Limits are kept in memory in the app process, which suits the single-host deployment; they reset when the app restarts.

The client IP comes from the TCP connection, or from `X-Forwarded-For` when `PC_TRUST_PROXY=true`. `compose.yaml` sets that because the app is reachable only through Caddy. Never enable it when clients can reach the app directly: they could then pick their own IP and evade the limits.

## Podman

Docker Compose works with Podman through Podman's API socket:

```sh
systemctl --user enable --now podman.socket
export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/podman/podman.sock
make dev-up
```

Rootless Podman can't bind ports 80 and 443, which the production `compose.yaml` uses. Use an override file with other ports for local testing.
